Foundations

Zero: what a browser extension actually is

An extension is a folder of web files — HTML, CSS, JavaScript — plus one JSON file called a manifest that tells the browser what those files are for. The browser reads the manifest, then runs your code in several separate places at once. Almost every confusing thing about extension development comes from those places being genuinely isolated from each other.

Here is the vocabulary, all of which this codebase uses:

manifest.json
The declaration file. Names the extension, lists permissions, and points at every entry file. Manifest V3 (MV3) is the current format; V2 is being retired. Ours is MV3.
content script
JavaScript the browser injects into a web page you visit. It can read and change that page's DOM. This is how every on-page feature here works.
isolated world
The crucial catch: a content script shares the page's DOM but not its JavaScript. You cannot read the page's variables, and it cannot read yours. Two heaps, one document.
background service worker
A script with no page attached, running on the extension's own behalf. In MV3 it is event-driven and the browser kills it when idle — so it can hold no long-lived state in memory.
devtools page
An invisible page that loads once per open DevTools window. Its only job is to register panels.
panel
A custom tab inside DevTools, beside Elements and Network. We ship two: AD Network and PD Inspector.
host permission
Permission to act on a specific site. Without it, a content script cannot be injected and a cross-origin fetch is blocked.
optional host permissions
Permissions declared as available but not granted until the user approves them at runtime. This is the model this extension uses — it ships with none granted.
chrome.storage
The extension's own key–value store, shared across all its contexts. .local persists; .session clears on browser restart. Not the same thing as the page's localStorage.
chrome.scripting
The MV3 API for registering content scripts at runtime rather than hardcoding them in the manifest.
web_accessible_resources
The list of extension files a page (or a content script) is allowed to load by URL. Anything not listed is unreachable from the page side.
document_idle
The injection timing we use: after the DOM is parsed, roughly when the page's own scripts have settled. Later than document_start, and—as you'll see—the source of a real bug.
Foundations

The three worlds, and what may cross between them

This is the single most important picture. A beginner's questions — why can't my content script read the app's state? how does the panel see requests? why does anything need a relay? — all resolve here.

Three consequences that shape the whole codebase:

  • The content script must work through the DOM alone. It cannot call an Angular component method. That is why json-editor/sync.js drives inputs by dispatching real events instead of setting model values, and why the PD Inspector fetches configs over HTTP rather than reading them out of the running app.
  • The background worker is stateless. Anything it must remember goes into chrome.storage, because the browser will shut it down between events.
  • Firefox will not give a DevTools panel chrome.tabs. So the PD panel sends its commands to the background worker, which forwards them to the page. That is the __pdRelay handler in background.js — pure cross-browser plumbing.
Orientation

What this extension actually does

It augments Service Designer, a web platform with two authoring tools: Automation Designer (AD), where engineers build backend methods as chains of steps, and Page Designer (PD), where they build UI pages from components. The extension adds engineering conveniences to both, plus two DevTools panels.

It runs on three route prefixes, each with its own bundle:

RouteBundleWhat it adds
/automation-designer/*ad-content.jsTitle updater, keyboard shortcuts, JSON input editor, output copy, textarea editor, cURL autofill, settings modal
/ui-designer/*pd-content.jsTitle updater, shortcuts, output copy, textarea editor, settings — AD-only features are not even bundled
/pages/*pd-inspector.jsThe engine behind the PD Inspector panel: point at a rendered page, learn which PD component drew it

Two facts worth internalising early, because they explain many decisions:

Self-contained

The extension talks to no third-party service. There is no companion server, no CLI, no cloud API. Everything it knows about a method or a page it reads from the site you are already signed in to, reusing that page's own session. This is why ad-api.js has an elaborate three-tier auth strategy instead of just holding a token.

No hardcoded sites

The manifest declares zero granted host permissions. Every origin the extension can touch is one you added on the options page and approved in a browser prompt. Ship it to a stranger and it does nothing until they configure it.

Manifest & background

The runtime host model

The conventional way to write an extension is to hardcode the sites in manifest.json. This one does not, because the sites are customer environments that change. Instead the manifest declares only the capability:

"permissions":               ["activeTab", "scripting", "storage"],
"optional_host_permissions": ["*://*/*"],
"content_scripts":           // absent entirely

The real list lives in chrome.storage.local under sdExtensionHostsV1, and the background worker continuously reconciles reality against it.

Two subtleties that took real bugs to find

Seeding. Uninstalling an extension wipes its storage — and in Firefox, loading a temporary add-on uninstalls the previous copy. So every rebuild during development lost the site list. The fix: an optional, gitignored sites.default.json shipped inside the extension folder, restored by onInstalled when storage has no host key at all. Note the precision of that condition — an explicitly emptied list stores {hosts: []}, which is present, so it is never re-seeded over.

The browser is the authority on grants, not storage. A seeded entry is written enabled: false, because a permission cannot be restored without a user gesture. On every render the options page calls chrome.permissions.contains for each host and reconciles the stored flag against the answer — so a host revoked outside the page shows a Grant button, not a stale Revoke.

Panels are gated too

devtools_page runs once per DevTools window, not per host — so without a check, the AD Network and PD Inspector tabs would appear on YouTube. devtools-page.js reads the current host, compares it to the allowed list, and only then calls panels.create. It re-checks on navigation and on storage change, so panels appear the moment you reach an allowed site without reopening DevTools.

Content script

The core: four small modules

Every on-page feature is a module exporting start(), which returns its own stop(). That one convention is what makes live toggling possible.

bootstrap.js — the lifecycle owner

Both designer bundles call bootstrap() with a map of feature name → starter function. It keeps a Map of active stoppers, and on every settings change starts what should be on and stops what should be off.

One detail is deliberate and hard-won: if a starter throws, bootstrap logs loudly and rethrows rather than swallowing. An earlier version left nothing in the active map on failure, so the next settings pass silently retried — and the textarea overlay ended up permanently dead until you toggled the setting by hand, with no error anywhere. The comment in the source names that incident.

settings.js — one store, many contexts

Feature toggles and editor defaults live in chrome.storage.local, not localStorage. The reason is scope: localStorage is per-origin, so each designer host kept a separate copy of your preferences. chrome.storage is extension-wide, so the options page, content scripts, panels and background all see one live value. A one-shot migration copies any pre-existing localStorage blob on first run and deletes it.

Reads are synchronous against an in-memory cache with a subscribeSettings observer, because storage is async but a feature needs to start now. Subscribers therefore fire twice on boot: once with defaults, once with the real stored values. Every value passes through sanitizeSettings, which iterates the default keys only — so a setting removed from the code drops out of a stored blob harmlessly.

observer.js — one MutationObserver for everything

A single shared MutationObserver on document.body with a subscriber set. Features that need to react to DOM churn subscribe; they do not create their own observers.

Optimization

The 2-second fallback poll used to run every subscriber unconditionally — re-scanning a large method forever, even while you sat still. It now computes a cheap fingerprint first, document.getElementsByTagName('*').length, and skips the work when it hasn't changed. Reading the length of a live HTML collection is far cheaper than querySelectorAll('*'), which materialises an array of every node. It misses same-size swaps — acceptable for a safety net whose main job is already done by the observer.

state.js and logger.js

state.js is a plain mutable object of cross-module handles (the open modal, the current toast). logger.js is a DEBUG-gated console wrapper. Both are small on purpose.

Content script

Feature by feature

The hover overlay — the most important file in the repo

ui/hover-overlay.js is a factory: give it a matcher and a list of buttons, get back a single floating controls element that follows the pointer. Two features use it (textarea editor, output copy) and it is the pattern any future one should follow.

What it guarantees, and why each matters:

  • Injected DOM is O(1), not O(matches). One controls node for the whole page.
  • The page's own markup is never touched. No wrappers, no added classes, no inline position, no marker attributes.
  • No scanning. Capture-phase delegation on document means a textarea added later is picked up for free — so these features do not subscribe to the MutationObserver at all.
  • Only one element is ever measured. A single getBoundingClientRect() per reposition.
  • The resolver gets the event, not just the node. Which is the only way to reach a control that dispatches no pointer events of its own.

Three implementation details are worth understanding because they encode real browser behaviour:

realTarget(event) uses event.composedPath()[0] rather than event.target. When an event crosses a shadow-root boundary, target is retargeted to the shadow host; the first entry of the composed path is the element actually under the pointer.

scheduleReposition() uses requestAnimationFrame and a 32 ms setTimeout, whichever fires first. rAF is the correct primitive — it runs just before paint, after layout settles — but it is suspended entirely in backgrounded tabs and headless rendering, where a missing frame would leave the overlay floating over the wrong element.

Buttons call preventDefault() on mousedown, so clicking one does not pull focus out of the textarea — otherwise the caret position an editor wants to restore is already lost by the time the click lands.

Textarea editor

The overlay offers Open and Copy; Open launches a CodeMirror 6 modal. Buttons shrink for a box under 36 px tall so they don't cover its content.

Published methods count. A published AD method renders its steps as non-editable fields, and reading a long SQL step in the large editor is exactly when you want this. The overlay used to refuse any readonly or disabled textarea, so it only ever appeared on drafts. It no longer does — the modal already refuses to write back to a read-only source, marking the subtitle (read only) and disabling Save.

Why that needed more than deleting a check

A disabled control dispatches no pointer events — the browser retargets the hover to its nearest enabled ancestor, so document-level delegation never sees the textarea at all. Hit testing is not suppressed the same way, so resolveTarget now also receives the originating event and falls back to document.elementFromPoint. Verified headless: elementFromPoint does return a disabled textarea. The coordinate check matters too — focusin carries no clientX, and without the guard every focus would hit-test the viewport's top-left corner.

The interesting part is language detection. There is no “auto” option — auto is always the behaviour, and the dropdown reports what was detected (with a one-off override that is deliberately not persisted, since a stored default would only fight the detector). Ordering is load-bearing:

JSON → SQL → Java → SpEL → Python → JavaScript → plain
  • SQL before SpEL because AD's SQL steps routinely interpolate SpEL placeholders — select id from x where y = '#{userId}' — and testing SpEL first highlighted every such statement as SpEL.
  • Java before SpEL because SpEL's T(java.lang.Math) shares vocabulary with Java, but Java source also carries package and modifier syntax a SpEL expression never has.
  • Python before JavaScript because both use class, import and return; the Python patterns are colon-terminated blocks and Python-only keywords, so they get first refusal.

JSON checks that the brackets are a matching pair — { … ] is neither an object nor an array — then tries JSON.parse. A document mid-edit (trailing comma, unclosed string, single-quoted key) won't parse but is still JSON to the person typing it, so a failed parse falls back to requiring structural evidence: a "key": pair, an empty literal, or an array opening with an object, array, string or number. A prose paragraph in braces stays plain.

JSON input editor most fragile

Edits all of a method's test inputs as one JSON document. extractor.js walks the DOM for INPUT_LIST_* ids (with two fallbacks) to produce {key, value, type, control}; sync.js writes values back type-aware across Text, Number, Integer, Boolean, Date, DateTime, Json, Array, Map and StructuredData.

Everything is driven through the real UI — native value setters plus dispatched events for plain fields, simulated clicks for the exp-* custom widgets, programmatic calendar navigation for date pickers — and then read back to verify. The file's own header says why there is no shortcut: window.ng is not exposed on the production build, and __ngContext__ is opaque, so driving Angular component instances directly is not available.

The listener is bound to window, and ensureShortcutListener() removes before adding — so it can be re-asserted on DOM churn without ever stacking twice. That self-healing replaced a flag-guarded attach that could go stale, leaving shortcuts dead until a settings toggle re-attached them.

cURL autofill

The AD Network panel's Open action base64-encodes a request body into a _sdx_autofill URL parameter. On the designer page the content script reads it, immediately strips it from the URL with history.replaceState, waits for the page title to change (the app's signal that the method has loaded), then polls until inputs exist and calls the same syncJSONToInputs the JSON editor uses. The parameter is produced and consumed entirely within this extension.

DevTools

AD Network panel

A Network-tab-style list scoped to /rest/api/automation/chain/ requests. Its difficulty is that the API extensions get is weaker than the one DevTools uses for its own Network tab, so the panel reconstructs the missing pieces from three sources.

Why the timestamp is parsed, not compared as a string

This is the kind of bug worth studying. Browsers emit HAR start times in local time with a UTC offset — …T17:04:56.789+05:30. Two timestamps carrying different offsets sort lexicographically in the opposite order to the instants they represent: 12:34:57+00:00 sorts before 17:04:56+05:30 despite being a second later. The same problem breaks dedup, because the replayed and live copies of one request may be formatted differently. startedAt() parses everything to epoch milliseconds, and both the key and the sort use that.

Three sources for a response body

Rows used to hang forever on “Loading response…”. The cause: getContent() is allowed to simply never invoke its callback. The panel now tries har.response.content.text (the only source for backfilled rows), then getContent() raced against a 3-second timeout, and if neither produces anything it says so — distinguishing a cancelled request from a body DevTools no longer retains.

Cancelled is not pending

An entry delivered by onRequestFinished is by definition finished, so a status of 0 means cancelled, not in-flight. It renders as a red canceled pill, matching the built-in Network tab's wording.

The pending feed, and why it needs page-heap access

chrome.devtools.network only fires on completion, so a slow or hung request is invisible while it is alive. pending-capture.js injects an IIFE via inspectedWindow.eval that wraps the page's own fetch and XMLHttpRequest, keeping a map of live chain requests on window.__belzADPending. The panel polls that map twice a second. The wrapper is idempotent per page context and re-installed on navigation.

Note what this costs: the injected script cannot reference any module state, because it runs in a different heap. That is why its chain-URL regex is duplicated inline rather than imported — syncing it would require a second eval round-trip.

Two origins, not one

ad-origin.js distinguishes apiOrigin (the inspected window's own origin — whatever host fired the request can answer questions about it) from designerOrigin (where the Automation Designer UI lives). On split public/staff-portal deployments these differ; the user records the mapping once per site on the options page. Nothing is hardcoded.

DevTools

PD Inspector

Point at any element on a published page and learn which Page Designer component drew it. The engine runs as a content script on /pages/*; the panel is the UI. This feature was rebuilt from scratch after research disproved its original design.

How a published page is assembled

A published page renders from a compiled config fetched from /rest/api/public/pagedesigner/deployable/pages. That config embeds components by name (“symbols”), each with its own config, fetched recursively into a graph.

Two findings changed the design:

  • The app shell is a separate page. The navbar and sidebar live in an ordinary PAGE whose layout contains a router-outlet node — and the content page does not reference its own container, so no amount of symbol recursion finds it. It has to be looked up separately by the first path segment. Detection must be config-side: one environment has three router-outlet elements in the DOM and zero in any of its 392 configs, because Angular emits its own.
  • URLs embed route parameters. A record id in .../LT-261/<uuid>/details means the literal path matches nothing; the page is registered under the template .../LT-261/:id/details. The endpoint exposes the route table, and matchRoute picks the match with the fewest parameters — the most specific one.

What failed, and why it is recorded

The runtime emits an <exp-layout class="exp-layout-use-sibling"> marker element before each thing it renders, which looked like a perfect structural map of the config. Three alignment attempts were measured and abandoned:

ApproachResult
Flat zip — marker[i] ↔ node[i]14% agreement
Sequential consumption with subtree skipping9% consistency
Tree walk matching by tag2% coverage

The root cause is that markers are a superset in some places and a subset in others: the runtime emits markers for its own internal markup (a config node with zero children renders a wrapper containing a marker for an element absent from the config), and an unrendered subtree — a closed dialog — emits nothing below its own marker.

What works: className as ground truth

A node's static props.className survives into the rendered element's class list. That is checkable fact, not inference — 168 of 354 composed config nodes on the reference page carry one, across 82 distinct strings.

The judgement call

When several config nodes share a className and several elements match, pairing them by document order is only sound if the counts agree. Pairing regardless reaches 98% coverage — but a generic overflow-hidden anchor with 18 candidates landed inside the sidebar and attributed the whole sidebar to the shell instead of the header component containing it. Because resolution takes the nearest anchor, a wrong near anchor shadows the correct outer one. Strict pairing costs 1% of coverage and fixes ownership. A wrong anchor is worse than none.

New finding: 620 KB parsed on every page load

This surfaced while evaluating build frameworks and has nothing to do with them. It is the largest remaining optimization in the codebase.

The fix, and the trap in it

Build features/textarea-editor/modal.js as its own chunk and have index.js load it on first use:

const mod = await import(chrome.runtime.getURL('dist/textarea-modal.js'));
mod.openTextareaEditor(textarea);

This needs a web_accessible_resources entry. Firefox supports dynamic import in content scripts and requires the same declaration, so the approach is cross-browser — worth verifying on Zen, which is the daily driver here.

Do not build it as a separate invocation

The current build loop runs one bun build per entry, and following that pattern here would be a correctness bug, not just duplication. modal.js imports core/state.js, core/settings.js and ui/modal-lock.js — all module-level singletons. A separate bundle gets its own copies, so state becomes a different object, subscribeSettings a different subscriber list, and the modal lock a different counter. It must be one bun build --splitting call across both entries so the shared modules land in a shared chunk. That means build.mjs moves from one-invocation-per-entry to a grouped call, and the emitted chunk names must be covered by the web_accessible_resources entry.

Status Recorded in tasks.md, not yet implemented — it is an architecture change to the build, and worth doing deliberately.

Decisions

Why JavaScript and not TypeScript

This is a deliberate choice, not an omission — and it is worth being honest that it cuts both ways.

The reasons it holds here

The hard parts are not type errors. The genuine risk in this codebase is that .header_banner stopped existing in the upstream Angular app, or that INPUT_LIST_* ids changed shape. document.querySelector('.header_banner') returns Element | null whether or not TypeScript is involved; no type system catches a selector that has gone stale. Every fragile edge here is a runtime assumption about somebody else's markup.

External JSON cannot be honestly typed. The chain v1/v2 responses and the deployable page configs are third-party payloads of unverified shape. The code already defends with normalizers — firstString(raw.name, raw.aliasName, metadata.name), defensive JSON.parse in try blocks, stub entries when a component fetch fails. Writing interfaces for those shapes would produce assertions, not guarantees, and a confidently wrong assertion is worse than an honest unknown.

The build stays trivial. Eight entry points, one bun build each, 0.44 seconds, no config file, no compile step to debug. Adding TypeScript adds a toolchain to a build that currently has none.

The intent is already documented. There are 58 JSDoc annotations — 33 @param, 17 @returns, 8 @typedef — concentrated exactly where they earn their keep: the module boundaries. hover-overlay.js documents its whole config object; resolve.js defines an IndexedNode typedef; config.js defines PageContext, PageConfig and ComponentConfig. Editors give IntelliSense from those without a build step.

Extension code is boundary-heavy glue. Most of it is chrome.* calls, DOM manipulation and message passing — areas where the value of static types is lowest and the ceremony highest.

The honest counter-argument

Where TS would genuinely help

json-editor/sync.js is the most fragile file in the repo — 596 lines returning {success, warnings, errors, counts, failed, missing} through many type-specific branches. A discriminated union over the input types would catch real mistakes there. So would typing the IndexedNode records in resolve.js. If TypeScript is ever adopted, those two files are where to start — not a wholesale conversion.

A cheaper middle path exists and is worth considering first: turn on checkJs with the JSDoc that is already written. Same checking, same editor experience, no build step, no file renames.

Decisions

Framework evaluation — the verdict

Three tools were assessed against measured facts about this repo rather than in the abstract. All three are a no, for different reasons.

No

wxt.dev

Vite-based. Requires restructuring src/ into its entrypoints/ convention and adds auto-imports — implicit code, a downgrade for a codebase this explicit. Its content-script ESM support is documented as work-in-progress, which is exactly what the lazy-load above needs. Costs a restructure, doesn't buy the thing that matters.

No

extension.js

Rspack-based, and the least invasive — built to adopt existing extensions. The real win is dev with HMR and an auto-launching browser, removing the manual reload step. Against that: it swaps a 0.44 s build we own outright for a large toolchain, and displaces pack.mjs, which is hand-tuned for the gecko id and the dual background style.

Later

webdriver.io

The only one filling a real gap — there is no test suite. But it cannot drive DevTools panels, the same restriction that killed the panel-focus shortcut, and the two panels are half this extension's surface. Chromedriver in CI for content-script coverage only.

Better first move on testing

bun test, in-repo, zero new dependencies — bun is already the toolchain. The throwaway harnesses written while building the last few features were all pure-function tests and belong here permanently: classifyChainUrl, detectLanguage (54 cases), buildConfigIndex (25 assertions), sync.js type coercion. That is where the regressions actually are. Revisit WebdriverIO only if the DOM-integration layer starts breaking in ways unit tests miss.

Build

Build and release

CommandDoes
bun installInstall dependencies (~5 MB, all CodeMirror)
bun run buildBundle to dist/, then pack build/chrome/ and build/firefox/
bun run build:distdist/ only
bun run devWatch mode for content scripts and the AD panel

Why one bun build per entry. A single shared build would mirror the src/ subdirectories into the output; building each entry separately lands everything flat in dist/, which is what the manifest paths expect. (This is exactly the pattern the lazy-load finding says must change — carefully.)

Why the non-ASCII escape pass. scripts/escape-non-ascii.mjs runs over every bundle for extension-loader compatibility.

Why two output trees. The root manifest.json is a template carrying both background styles. pack.mjs writes a Chromium copy (deleting background.scripts) and a Firefox copy (deleting background.service_worker, adding browser_specific_settings.gecko with the AMO id and update URL). Always load from build/, never the repo root — the root manifest is valid for neither browser as written.

Why the panel HTML sits at the repo root. Chromium resolves devtools_page-relative paths from the extension root; Firefox resolves them relative to the devtools page itself. A dist/panel.html would become dist/dist/panel.html in Firefox and load blank.

Maintenance

Where this breaks first

  • DOM coupling. Selectors in config/constants.js depend on the AD/PD app's current class names. When the upstream UI changes, these break before anything else. Smoke-test on a real AD and PD page after touching them.
  • Custom control internals. AD's date pickers and exp-select widgets dispatch synthetic events on internal state changes; sync.js has hand-tuned event sequences that are easy to disturb.
  • The re-arm workaround. Both overlays re-register their listeners at 1 s, 3 s and 6 s because the first registration at document_idle was observed never to receive events. It works, but nobody has established why the listeners are orphaned. This is the top open item.
  • Inline styles in modals. Heavy use of inline style strings; refactors here are noisy. Keep them confined.

Also worth reporting upstream

Not an extension bug

/rest/api/public/pagedesigner/deployable/pages serves every page and component config for a domain — roughly 45 MB across the two dev environments — with no authentication at all. Found while researching the PD Inspector. The platform owners should know.

The maintainer contract

AGENTS.md is the canonical map of this codebase and carries a standing rule: when you make a meaningful change — new feature, changed selectors, sync behaviour, manifest scope, file layout — update it in the same commit. README.md is the public-facing version. This page is the explanatory one.
