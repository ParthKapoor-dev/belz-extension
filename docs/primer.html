Companion to belz Extension Internals

belz Extension Primer

Every term in that document is an ordinary idea with an intimidating name — and most of them you already know from building REST APIs. Here they are, in the words you already have.

A note before we start. You said you usually skip these words and move on. That instinct is more common than anyone admits, and the reason it persists is that jargon is compression: a word like “reconcile” packs a whole paragraph into three syllables. That's useful once you know the paragraph and impenetrable before. Nothing below is hard. It's just unpacked.

Since backends are your solid ground, I'll anchor each term to something you already do there. Those anchors aren't loose metaphors — in most cases they're literally the same idea, borrowed by a different community.

PART 1 · TERM 01

Reconcile

reconcile

Make reality match the plan — whatever reality currently looks like.

You have a list of what should exist, and a list of what does exist. Reconciling means comparing the two and issuing whatever add/remove/update calls close the gap. Crucially, it doesn't care how things drifted apart. It just fixes them.

You already know this as

An idempotent sync job. Imagine a nightly task: read the subscriptions table, list the active mailing-list entries at your email provider, then add the missing ones and delete the extras. You don't track events (“user subscribed”, “user churned”) — you just compare the two lists.

It's also exactly why PUT is idempotent and POST isn't. PUT /users/7 says “make user 7 look like this”. Run it five times, same result. That's the reconcile mindset applied to one resource.

Here The user's site list lives in storage. The browser separately holds a set of registered content scripts. reconcileContentScripts() reads the list, asks the browser what's registered, and diffs them.

Why not just do it when the user clicks Add?

This is the real lesson, and it generalises far beyond browser extensions. The obvious design is event-driven: user clicks Add → register a script. User clicks Revoke → unregister it. Simple, and it works… until it doesn't:

  • The browser restarts. Were registrations kept? Partly, sometimes.
  • The user revokes the permission in browser settings, never touching your page.
  • The extension updates and its file paths change.
  • Your registration call failed and nobody noticed.

Each of those is a separate bug needing separate handling. With reconcile, there is one code path, and you simply run it whenever something might have changed. Every one of those scenarios is already covered, because the function never assumed a starting state.

The reconcile pattern is everywhere once you spot it: Kubernetes is essentially one enormous reconcile loop, Terraform is reconcile for cloud resources, and a database migration runner is reconcile for schema. Recognising it is a genuine upgrade in how you design systems.

PART 1 · TERM 02

Seeding

seeding

Putting starter data into an empty store so a fresh install isn't useless.

You already know this as

Database seeding. A seeds.sql or a db:seed command that inserts the default roles, the admin user, the country list — the rows the app needs to function but which no user would ever type in by hand.

Here Exactly the same idea, just with chrome.storage instead of Postgres. On install, if there's no site list, read sites.default.json and write those hosts in.

Why it was needed at all

Two browser behaviours combine into an annoyance:

  • Uninstalling an extension wipes its storage. Reasonable — you wouldn't want uninstalled extensions leaving data behind.
  • In Firefox, loading a temporary add-on (what you do when developing) counts as uninstalling the previous copy.

So every single rebuild-and-reload during development wiped the developer's carefully typed list of sites. Seeding restores it automatically.

A word about the word “subtlety”

That one isn't technical at all. A subtlety is just a fine distinction that's easy to miss and matters anyway. When a document says “two subtleties”, read it as “two small things that look unimportant but will bite you”. The next section is one of the best examples I know.

PART 1 · TERM 03

Absent is not the same as empty

This is the sentence you quoted:

“Note the precision of that condition — an explicitly emptied list stores {hosts: []}, which is present, so it is never re-seeded over.”

Here's the problem it solves. Seeding must only happen for a brand-new install. But how do you tell “brand new” from “the user deliberately deleted every site”? In both cases there are zero sites.

If you get this wrong, the bug is genuinely maddening: the user removes their last site, reloads, and it silently comes back. They remove it again. It comes back again. The extension appears haunted.

The fix is to notice there are three states, not two:

In code the whole subtlety is one line — testing for the key, not its contents:

// right: is the key there at all?
if (stored && stored[HOSTS_STORAGE_KEY]) return;   // configured before, don't seed

// wrong: this treats "emptied on purpose" as "never configured"
if (hosts.length === 0) seed();
You already know this as

You meet this constantly in APIs and just may not have named it. GET /users/7/tags returning 404 (no such user) is a different answer from 200 [] (user exists, has no tags). Same in a PATCH body: {"nickname": null} means “clear the nickname”, while omitting the field entirely means “don't touch it”. And in SQL, NULL is not ''.

The general rule: “no value” and “the empty value” are different pieces of information. Collapsing them destroys the user's intent. Once you start noticing this, you'll find it in half the confusing bugs you meet.

PART 1 · TERM 04

Subscribers

subscriber

A function that has asked to be called when something changes.

You keep a list of functions. When the thing changes, you loop the list and call each one. That's the entire mechanism — there is nothing else to it.

You already know this as

Webhooks. A client registers a callback URL; when an order ships, your server POSTs to everyone registered. Subscribers are the same design with the network removed: instead of a URL you store a function, and instead of an HTTP request you just call it.

Also: SQL triggers, pub/sub topics, and the listener list behind any event emitter.

Here subscribeSettings(fn) for settings changes, and subscribeObserver(fn) for DOM changes.

The whole implementation

Jargon makes this sound like a framework. It's four lines:

const listeners = new Set();

function subscribe(fn) {
  listeners.add(fn);
  return () => listeners.delete(fn);   // call this to unsubscribe
}

function notify(value) {
  for (const fn of listeners) fn(value);
}

Two details worth absorbing, because both show up in real systems:

Subscribe returns its own undo. subscribe() hands back a function that removes the listener. That's a widespread convention — the thing that creates a resource also gives you the way to release it, so you can never lose track of it. In backend terms, it's the DELETE that pairs with your POST, handed to you at creation time.

Why bother at all? Because it inverts who knows about whom. Without subscribers, the settings module would need to import every feature and call them directly — so adding a feature would mean editing the settings module. With subscribers, settings knows nothing about features; features announce their own interest. That's called decoupling, and it's the same reason you'd rather emit an order.shipped event than have your order service import the email service, the analytics service and the loyalty service.

PART 1 · TERM 05

Polling

polling

Asking “has it changed yet?” over and over, on a timer.

You already know this as

The cron job that hits GET /jobs/123/status every 30 seconds until it says done. Compare with the alternative: the job service calls your webhook the moment it finishes. Polling is you asking repeatedly; events are being told once.

Polling

Simple, works even when the other side offers you nothing. You control the frequency.

Costs work every tick even when nothing changed, and you learn about changes up to one interval late.

Events / push

Zero cost while idle, and you find out immediately.

Requires something willing to notify you — and if it misses an event, you may never find out at all.

Mature systems often use both: events for speed, plus slow polling as a safety net for missed events. That is precisely what this codebase does.

How it plays out here

The event mechanism is a MutationObserver — a browser feature that calls you when the page's HTML changes. Efficient, and free when nothing happens. But it watches document.body, and it cannot see inside a shadow root (a private DOM subtree a component can hide inside itself — more on that later). So changes in there would be missed entirely.

Hence a 2-second poll as backup. And here's the clever part, which is worth stealing:

function pollTick() {
  const fingerprint = document.getElementsByTagName('*').length;
  if (fingerprint === lastFingerprint) return;   // nothing changed — stop here
  lastFingerprint = fingerprint;
  fireAll();                                     // only now do the expensive work
}

Before doing anything costly, it computes something very cheap — the number of elements on the page — and bails if that number is unchanged. Counting is far cheaper than re-running every subscriber.

You already know this as

ETags and If-None-Match. Rather than downloading a whole resource to see if it changed, the client sends a cheap fingerprint and the server replies 304 Not Modified. Identical idea: a cheap check gates the expensive operation.

Same family: Last-Modified, checksums before a file sync, and comparing a row's updated_at before recomputing a cache.

And the honest limitation

Counting elements misses a change that swaps one element for another, leaving the total identical. The code says so out loud, and accepts it — this is only a backup for the rare shadow-DOM case, and the next structural change will catch it. Knowing what your optimization doesn't cover, and writing it down, is a mark of good engineering rather than a weakness.

PART 1 · TERM 06

SPA — Single Page Application

SPA

A website that loads once and then rewrites itself with JavaScript, instead of fetching a new page from the server for every click.

You already know the alternative

The traditional model is the one your REST brain expects: browser asks for /orders, server renders complete HTML, browser throws away the old page and displays the new one. Every click is a full round trip and a fresh document.

Three consequences drive much of this codebase's design:

  • Your script runs once, the page changes forever. The content script is injected at page load. If you scan for textareas then, you miss every one rendered afterwards — which is most of them.
  • The URL changes without a page load. Navigating from one page to another inside the app doesn't re-inject anything. That's why the PD Inspector checks location.pathname every 1.5 seconds instead of trusting a navigation event.
  • The app starts after the HTML arrives. The shell downloads fast; the JavaScript then has to run and build the real interface. That gap is where the extension lands, and it's the whole story of step 07 in your chart.
PART 1 · TERM 07

Bootstrapping

bootstrap

The startup sequence that takes a system from “code is loaded” to “ready to do work”.

From the old joke about pulling yourself up by your own bootstraps — a system that has to get itself running before it can run.

You already know this as

Your API server's boot: read config → connect to the database → run migrations → register routes → start listening on the port. Until that finishes, requests get connection-refused. Nobody calls it “bootstrapping” in a tutorial, but that's what it is.

Here The extension's bootstrap() reads settings and starts the enabled features. Separately, the Angular app does its own, much larger bootstrap. Two systems, each booting, in the same tab.

And that is the bug

The extension's content script is injected at document_idle — roughly “the HTML is parsed and things have gone quiet”. That sounds late. But for an SPA, the HTML is nearly empty and parsing it is trivial, so document_idle arrives while the app has barely begun. The extension finishes booting before the app it's supposed to augment.

You already know this as

A race condition — two things happening in an order you don't control, where one order works and the other doesn't. You've met it if you've ever had a service start before its database was accepting connections, or seen a test pass alone and fail in the suite.

The standard cures are the same everywhere: retry (try again in a moment), wait for readiness (poll a health check until it answers), or re-establish on a signal. This codebase uses the first — and is honest that it's a patch, because nobody has yet worked out why the early listeners are ignored.

PART 1 · TERM 08

Overlay

overlay

An element drawn on top of the page, positioned to look attached to something — without actually being inside it.

Think of a sticky note laid on a book page, versus writing in the margin. The sticky note can be moved to any page and peeled off leaving no trace. Writing in the margin changes the book.

Here One small floating element holds the Open and Copy buttons. When your pointer enters a textarea, the code measures where that textarea is on screen and moves the floating element over its top-right corner. It looks attached. It never was.

Mechanically it's two pieces:

  • position: fixed — the element is positioned relative to the window, not to whatever is around it in the HTML.
  • getBoundingClientRect() — asks the browser “where is this element on screen right now?”, giving top/left/width/height in pixels. Copy those numbers onto the floating element and it lands in the right place.

Why this is the whole performance story

The alternative — the original design — was to inject a wrapper and a button into every textarea. On a method with 120 textareas that's roughly 480 extra elements, and it edits the app's own HTML, and it needs re-scanning every time the page changes to catch new ones.

With one overlay: one element, always. The page's HTML is never touched. And because it works by asking “what is the pointer over right now?”, a textarea added five minutes later is handled with no registration and no scan.

You already know this as

The difference between O(n) and O(1). If you've ever replaced a loop of 120 single-row INSERTs with one batch statement, or noticed an N+1 query problem in an ORM, this is the same instinct: the cost should not grow with the size of the input if it doesn't have to.

PART 1 · TERM 09

Timers, and the honest problem with 400 ms

“Timers: settings button @400 ms, JSON button @1 s” simply means:

setTimeout(() => injectSettingsButton(), 400);   // do this 400ms from now

Two functions, which you'll see constantly:

setTimeout(fn, ms)

Run fn once, ms milliseconds from now.

setInterval(fn, ms)

Run fn every ms milliseconds, forever, until you call clearInterval.

The settings button has to be inserted next to the app's page title. At the moment the extension boots, that title doesn't exist yet — the app hasn't rendered it. So the code waits 400 ms and tries then.

Why this is a code smell, and worth recognising

400 is a magic number: a value with no derivation behind it, chosen because it happened to work on someone's machine. It's a bet on timing. On a slow laptop, a throttled network, or a much larger method, the app may still not be ready at 400 ms — and the button silently never appears.

The sturdier principle: wait for a condition, not for a duration. Instead of “wait 400 ms then look”, say “tell me when the page changes, and look then”. This code actually does both — the timer is a first attempt, and a MutationObserver subscription retries on every DOM change, so the button appears eventually even if 400 ms was optimistic. The timer is the fast path; the observer is the correct one.

You have the same choice in backends: sleep(5) before hitting a service you just started, versus polling its /health until it answers. The second is longer to write and right.

PART 2

The chart, line by line

Now the whole thing should read differently. This traces one Automation Designer page from a cold browser start to a hovered textarea. Nothing below introduces a new idea — it's all Part 1, in order.

  1. 01

    runtime.onStartup → reconcileContentScripts()

    The browser starts and fires a startup event. The extension's background script wakes up and runs the reconcile from Part 1: read the saved site list, ask the browser what's currently registered, fix the difference.

    “Worker then sleeps” is important. In Manifest V3 the background script is not a long-running server — the browser shuts it down when it's idle and restarts it when an event arrives. So it can't hold anything in memory between events; everything it must remember goes to storage. If you've written AWS Lambda handlers, that's precisely the model: stateless, event-triggered, no persistence between invocations.

  2. 02

    page loads — DOM parsed, app scripts running

    You navigate to a designer page. The server returns HTML; the browser parses it into the DOM (the live tree of elements that JavaScript can read and change) and starts running the app's JavaScript. Nothing of ours yet.

  3. 03

    content script injected (document_idle)

    The browser inserts ad-content.js into the page and runs it. document_idle is one of three timing options — document_start (before anything), document_end (after HTML is parsed), document_idle (after that, when things have quieted down).

    Our file has no main(): the code at the top level simply runs, and the last thing it does is call bootstrap(). That's the extension's own startup sequence beginning.

  4. 04

    applyFeatureSettings(loadSettings(), 'init')

    Start the features the user has enabled. But reading chrome.storage is asynchronous — you ask, and the answer arrives later via a callback, the same way a database query doesn't return instantly. The settings haven't come back yet.

    So this first pass uses the defaults baked into the code. “Synchronous” here just means it happens immediately, in order, with no waiting. The features start optimistically now, and get corrected in a moment.

  5. 05

    storage callback → subscribers re-run

    Storage answers. Every subscriber (Part 1, term 04) is called with the real settings, and anything the user had switched off is stopped again.

    This is why a feature may briefly start and then immediately stop on page load — not a bug, but the cost of not making the user wait for storage before anything works. Backend equivalent: rendering a page from cache instantly, then re-rendering when the authoritative query returns.

  6. 06

    timers: settings button @400 ms, JSON button @1 s

    The two injected buttons need to attach to app markup that doesn't exist yet, so each waits before trying. See Part 1, term 09 — including why these numbers are a bet, and what backs them up.

  7. 07

    the host SPA finishes bootstrapping — AFTER us

    The punchline. The app we're augmenting only now finishes starting. We've been ready for a while, holding event listeners the page appears to ignore.

    Read “were observed to never receive events” carefully — that phrasing is deliberate. It means somebody watched it happen repeatedly but has not established the mechanism. Writing “observed” rather than “because Angular replaces the document” is a small act of intellectual honesty: it marks the difference between a measurement and an explanation. Get comfortable writing that distinction down; it's how you avoid building on a guess.

  8. 08

    overlay re-arms at 1 s / 3 s / 6 s, and on load + pageshow

    “Re-arm” means: remove the event listeners and add the same ones again. Someone noticed that toggling the feature off and on by hand fixed it — and toggling does exactly a detach-and-reattach. So the code does that automatically, a few times, spread across the first six seconds to cover a slow start.

    Three attempts rather than one because you don't know how slow the app will be; spacing them 1/3/6 covers a fast machine and a slow one without hammering. load and pageshow are browser events (page fully loaded; page shown, including when restored from the back button) — extra moments worth re-checking.

    The doc calls this “a workaround, not a fix”, and that's the right label: it reliably makes the symptom go away without anyone understanding the cause. Sometimes that's the correct engineering trade — but you write it down, so the next person knows there's a real answer still to find.

  9. 09

    steady state: zero polling, zero scanning

    Everything's up, and now the extension does nothing at all until you act. No repeated searching for textareas, no timers doing busywork. Move the pointer, focus a field, scroll, or let the app change the page — only then does any code run.

    This is the goal for any code living inside somebody else's application: invisible when idle. The equivalent in your world is a background job that sits on an empty queue costing nothing, versus one that wakes every second to ask whether there's work.

PART 3

What's coming in the next sections

You asked what else to learn ahead of time. These appear later in the main document; here they are in advance so they don't stop you.

Events

event delegation

Instead of putting a listener on all 120 textareas, put one listener on the whole document and check what the pointer was actually over.

You know this: one route /items/:id rather than registering 120 separate routes. Fewer handlers, and it works for items that don't exist yet.

capture vs bubble

An event travels down from the document to the element (capture), then back up (bubble). You choose which leg to listen on.

Listening on capture means you hear it first — before the page's own handlers can cancel it. It's middleware that runs before the route handler.

shadow DOM

A component can hold a private, hidden DOM subtree that ordinary queries can't see into.

When an event escapes one, the browser rewrites its target to the outer component — “retargeting”. Hence composedPath()[0], which recovers the element genuinely under the pointer.

hit testing

“Which element is at pixel (x, y)?” — document.elementFromPoint(x, y).

Useful because a disabled field receives no mouse events at all, yet still occupies space; hit testing finds it when events cannot.

Controlling how often things run

debounce

“Wait until they've stopped for 250 ms, then act once.” Search-as-you-type: don't query on every keystroke, query when typing pauses.

throttle

“Act at most once every 500 ms, no matter how many events arrive.” Closest to backend rate limiting.

requestAnimationFrame

“Run just before the browser paints the next frame” — about 60× a second, aligned with the screen.

Right for moving something on screen. Suspended in background tabs, which is why the code pairs it with a timeout as backup.

coalescing

Fifty scroll events arrive; you only need to reposition once. Collapse the burst into a single piece of work.

Same as batching many small writes into one transaction.

Caching

TTL

Time to live — how long an entry stays valid. Here: fresh for 6 hours, usable up to 14 days.

stale-while-revalidate (SWR)

If data is old but not ancient, hand it over immediately and refresh in the background. The user gets an instant answer; the next request gets a fresh one.

It's a real HTTP Cache-Control directive — the same idea you'd put on a CDN.

eviction

What you throw out when the cache is full. Here: a cap of 800 entries, oldest discarded first.

dedup key

A string identifying “the same thing”, so you don't store one item twice. Here it's URL + start time.

A unique constraint, or the idempotency key you'd send with a payment request.

A few one-liners

HAR

HTTP Archive — a JSON format listing network requests with their headers, timings and bodies. Just a log format; nothing clever.

module singleton

A variable at the top level of a file exists once per bundle. Bundle the file twice and you get two independent copies — the trap in the CodeMirror finding.

ground truth

A fact you can check directly, as opposed to something inferred. The PD Inspector section is really an argument about preferring the first to the second.

negative control

Deliberately break the thing and confirm your test fails. Proves the test actually detects the problem rather than passing for free.

PART 3 · CLOSING

The habits underneath all of it

The terminology is the easy half. What actually separates engineers is a handful of habits, and they're all visible in the document you were reading:

  • Distinguish measured from explained. “Listeners were observed to never receive events” says: this is what happened, and I do not yet know why. Never quietly upgrade an observation into an explanation.
  • Absent is not empty. Whenever a value can be missing, ask whether missing and blank should mean different things. Usually they should.
  • Prefer a condition to a duration. sleep(400) is a guess about someone else's machine. Waiting for the thing you actually need is slower to write and doesn't break on a bad day.
  • Make repeated work safe. If a function can run twice with no harm, you stop needing to know how many times it ran — which removes a whole category of bug.
  • Write down what your fix doesn't cover. “A workaround, not a fix” costs one line and saves the next person hours.
  • Measure before believing. Three plausible approaches in the PD Inspector scored 14%, 9% and 2%. All three sounded right. Only measurement said otherwise.

One last thing, since you mentioned being scared off by these words. Every term here was invented by somebody who needed a short name for a thing they were doing anyway. There is no hidden layer of difficulty underneath — when a word looks impenetrable, it's nearly always a two-sentence idea with a bad name. Ask what the two sentences are.
